# M2.d：失败恢复与只读动作历史

普通主会话的压缩/开窗失败已经通过绑定 actionId + carrier messageId 的 fail_compact_turn 将 APPLIED 更新为 FAILED；执行前撤销维持 UNDONE，已完成/已结算动作不能被迟到失败改写。本节点补齐失败状态保存的可见性、恢复入口与窗口历史，不修改原生 Adapter 能力或冷却规则。实现与离线验证完成，真实 UI 验收仍归 M2.e；M2.c2/c3 的实机能力/连续记录继续未完成。

## 失败状态与恢复

消息的 compactAction 增加 failureReceipt=pending/saved/error。正常执行错误、启动 IPC 拒绝和执行后取消仍沿用原有失败落库入口；只有失败 IPC 返回成功才显示“失败/取消状态已保存”。保存失败会保留失败内容与回执警告，提供“重试保存状态”；并发点击不会重复发出同一条保存。重试状态保存只调用存储 IPC，不启动 CLI。

重开应用时，已确认保存的失败回执保留；未确认或仍在保存的回执显示为未确认，可手动重试。中断运行的动作仍标 unknown，不猜测为 FAILED，不开放失败重试来覆盖可能已经完成的动作。

失败/取消消息提供两个恢复选择，均要求失败状态已确认保存：

- 重新排队原消息：新发送记录保存 requestMessageId，以此定位当前会话内原 user 消息；兼容旧记录时只检查紧邻的 user 消息。保留精确文本与原模式，放回队首，不立刻调用模型，不复用旧 APPLIED/FAILED action。发送时仍走正常模型、授权、建议与冷却校验。有运行轮次、审批或排队动作时拒绝重新排队；缺失原消息、重复恢复或跨会话引用同样拒绝。
- 忽略本次失败：只记录本消息恢复提示已忽略，不将 FAILED 改为 DISMISSED、不清除原错误、不修改既有队列或节省事件。

失败记录和原生确认/费用字段均保留。原生压缩已确认但承载轮失败时，恢复同样只重新排队原用户消息；此前的原生用量和失败冷却记录不清零。忽略提示不等于关闭之后的新建议。

## 当前窗口动作记录

普通会话的上下文区域新增默认折叠的只读历史，context mode=off 时仍可查看过去记录。展开后读取，支持刷新；窗口切换、排队/完成/失败保存变化会重新读取，迟到的旧查询结果不会覆盖当前窗口。无数据、读取中和读取失败分别显示，刷新不发模型请求。

来源 ID 仅从当前原生 thread、session、请求 Provider/模型及角色匹配的助手消息提取，去重后最多 512 个。CLI 上报模型别名不改变原请求身份。后端 list_context_action_history_cmd 批量查询 source 或 newAttemptId 关联，同时核对 settlementV1.sessionId / queuedIntent.scope.sessionId，只返回最新 50 条 COMPACT/FRESH 摘要。新窗口可看到与自身 target 关联的入站 FRESH。旧记录若缺少可核实的会话元数据，不猜测归属；损坏 JSON 被排除，不扩成跨会话查询。

接口使用参数化查询，最多 513 个独立 SQL 参数，并限制输入 ID 长度。摘要只含动作 ID、源/目标、kind/status/trigger/method、时间和既有节省估算，不返回 estCostsJson、保留提示词或契约全文。没有新增写操作或迁移。界面明确 APPLIED 只是绑定执行，不表示完成或已证明节省；数值仍标为首轮反事实估算，未知值不显示为零。
