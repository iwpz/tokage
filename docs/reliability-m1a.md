# m1a：流水线状态可靠持久化实施记录

日期：2026-10-16。对应[可靠性优化计划](可靠性优化计划.md)的 m1a，验证范围为本机 macOS、单个 Tokage 进程。

## 问题与调整

原保存流程会同时发起多个 IPC 请求，Rust 使用固定的进程级临时文件名，导致并发请求互相覆盖临时文件。前端只向控制台报告失败；关闭窗口只关注防抖计时器，没有等待已经发出的写入。

- [x] 前端按工作目录与会话建立保存队列，入队时复制快照；后续修改不会改变已入队内容。防抖回调读取最新状态，避免旧回调把新状态覆盖掉。
- [x] 增加向后兼容的 `persistenceRevision`。从恢复文件的版本继续递增；Rust 在同一写锁内比较版本并替换文件，拒绝旧版本和内容不同的同版本请求。相同版本、相同内容允许重新同步后确认成功。
- [x] 后端使用独占创建的唯一临时文件；遇到旧临时文件跳过该名称。写完同步文件，再原子替换；Unix 下继续同步 execution 目录、.tokage 目录和项目根目录。失败时清理本次临时文件，保留错误供调用方处理。
- [x] 保存失败保留最新内存状态，流水线暂停派发；界面显示错误和“重试保存”。重试成功不自动恢复运行，用户可以继续执行。已完成全部任务的流水线继续时恢复为 `DONE`。
- [x] 窗口关闭先同步阻止默认关闭并停止新的任务认领；等待当前写入、最新快照以及等待期间新增的防抖内容。失败保持窗口打开；重复关闭请求共享同一次等待。
- [x] 恢复时保留 worktree 尝试次数和交付结果。保存恢复状态失败不再被 Rust 忽略；已保存的 `DONE` 任务保持完成，在途任务继续按既有规则转为 `INTERRUPTED`，不自动重新派发。

## 关键持久化边界

- 派发、原窗口修复、继续任务、审批后恢复：启动 CLI 前等待保存确认；新的派发还在创建工作区前保存任务认领。
- 审批：先保存仍待处理的决定意图，再写入审批记录；记录成功后保存 resolved 状态与允许命令，之后才安排恢复。必要保存失败时，原审批仍可重试。
- Worktree：创建前保存认领或尝试次数；创建后保存实际路径、分支、基线等元数据，启动 CLI 前再次确认。
- 验收和任务完成：进入验收、继续下一条验收命令、标记完成和推进下游均经过保存确认。
- 任务合并：提交与合并前确认当前记录已保存；合并结果日志及冲突任务安排保存后，才清理原工作区。
- 最终交付：保存 `merged` 结果后再清理集成工作区。合并已完成但保存失败时保留 `merged` 状态和工作区供重试；再次确认该交付不会重新发起合并。

## 保证边界与后续验收

文件替换保证读者看到旧的完整文件或新的完整文件。成功确认前执行文件同步，Unix 下执行目录同步；如果 rename 已完成、后续同步失败，调用方仍收到失败，须保留状态并重试，不能推断“写入完全没有发生”。同步调用不等于已完成硬件断电实验，也不能代替文件系统与磁盘的持久性保证。

本次运行了真实文件系统和保存途中终止子进程的自动化测试；界面提示由组件接线、类型检查和生产函数测试覆盖，未宣称已做桌面人工点击验收、真实 CLI 实机执行或物理断电验收。Windows / Linux 的目录同步与崩溃恢复仍需各自验证。

写锁覆盖单个 Tokage 进程内的全部保存入口，不支持据此宣称多个独立应用进程可共同编辑同一会话。Git / CLI 副作用与状态文件也尚不是统一事务：操作已经生效但进程在结果记录前退出的核对，以及恢复后的幂等推进，仍属于 m1d / m2e；不能从本项推导整条流水线已经具备恰好执行一次的保证。
