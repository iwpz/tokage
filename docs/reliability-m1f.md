# m1f：完成、验收与交付语义准确

## 行为与边界

- `DONE` 表示任务执行结束和产物保存；看板显示“执行结束”。它不再通过日志宣称用户已接受交付。任务未配置命令时可结束执行并推进依赖，但不会记为自动验收通过。
- 任务关卡与计划全量关卡共用 `runAcceptanceCommands`。每条命令都有 `passed`、`failed`、`error`、`cancelled` 或 `not_run` 结果；失败后停止执行余下命令，同时保留未执行项。取消后的迟到成功不能改变结论。旧记录缺少新增字段仍可读取。
- 计划交付区区分验收中、通过、失败、未配置、取消和证据失效，显示全部命令结果及输出。全量命令为空时 `fullGatePassed=false`；摘要在 Rust 和浏览器实现中均不再把缺失结果默认当作成功。跳过任务不计为已完成，也不能授权正常合并。
- 通过自动验收后仍需用户在现有确认框中选择合并。正常合并入口要求计划执行结束、全部任务 DONE、交付 ready、明确验收通过以及完整证据。旧 `fullGatePassed=true` 记录无法替代证据，需要重新验收。未提供绕过失败门禁的人工合并入口；导出补丁和保留分支继续保留原验收结论，不代表验收通过。

## 证据与重新验证

全量验收保存验收前后的 Git 内容快照，含工作目录、HEAD、磁盘内容及暂存区身份，并绑定命令集合、任务定义及任务状态。命令运行期间这些内容改变，或任务被取消，均不能生成通过证据；集成 worktree 不干净也不能通过交付验收。结果、逐条状态和证据随流水线持久化。

合并前前端重新核对快照、任务定义、状态及源分支 SHA。原生 IPC 再次核对源工作目录快照与分支 SHA，实际按验收提交 SHA 合并，避免检查完成后分支指针移动导致合并另一提交。只有合并成功才写 `merged` 和用户接受时间，并遵循 m1a 的持久化后清理顺序。

“重新验收”先清除旧证据，再执行新一轮检查；“取消验收”先使证据失效，再取消原生门禁进程。应用恢复时未结束的全量验收重置为 idle，打开看板后重新执行，不复用中途结果。任务关卡也检查运行前后内容变化，并在保存报告后再次核对范围证据，覆盖 worktree 和原地执行。

报告里的关卡摘要由实际运行结果覆盖模型文本。`firstPass` 不再固定写入 true：未配置关卡、修复或已有多次工作区尝试均不会记为首次自动通过；缺少报告时生成的交付占位报告也不假定首次通过。完整学习统计与首次通过口径核对仍属于 m3 的工作。

## 保证范围

这是代码与本地自动化验收，未执行真实付费模型或桌面手工端到端验收。命令必须在稳定的受保护内容上完成；格式化等命令修改被跟踪文件时，本次证据失效，需要先处理改动再重新验收。ignored 文件、仓库外副作用和外部服务状态不在 Git 快照证明范围。

快照只能证明检查边界的内容一致，不能证明命令自身充分、测试覆盖足够或命令运行期间外部进程曾短暂修改后恢复文件。跨进程所有权、外部编辑器竞争、合并完成但响应丢失等完整崩溃恢复仍由 m2e 收敛；本节点不宣称对这些情况提供事务级保证。
