# m2e：恢复与幂等性

日期：2026-10-19。本次验收限 macOS、本地文件系统、同一应用数据目录的单个应用拥有者，以及生产编排与原生组件的分层故障注入。未消耗真实模型额度；完整桌面强杀后恢复真实服务商会话的实机矩阵仍由 m2g 验收。

## 恢复原则与实现

- **先核对事实，再决定恢复。** 原生冷加载将原先在途的任务记录为 recoveryTasks；继续时读取原生运行 / 待派发状态、进程登记、提交凭据及原生会话可见性。已有 Git 事务进一步核对 worktree 分支、固定源提交和集成分支是否仍包含产物。无法确认时转 BLOCKED，保留文件并提供终端接手、重新验收或明确重规划的路径。
- **不把不确定的旧执行自动重跑。** 每个原生 turn 在异步检测之前以 create_new 建立、同步落盘一次性提交记录，同 ID 的重复 IPC 不再启动 CLI。待派发请求也算活动状态，取消为该 ID 设立栅栏，检测结束后的迟到请求不能启动进程。只有请求交给运行注册表以后才撤销待派发拥有权。
- **区分完成凭据与界面状态。** 收到 CLI 成功后、任何 gate / 提交之前，保存包含 turn、任务定义、计划定义、目录、输出、改动列表和费用信息的 completionReceipt。冷恢复有匹配凭据和原生 / Git 事实时，只重新验收，不再次调用模型；没有凭据、原生证据不明、分支 / HEAD 改变或 worktree 丢失时阻塞。恢复中不再因目录消失静默切换到主检出重新派发。
- **丢失派发响应不能触发第二次模型执行。** 前端将不确定的提交标记为需要恢复，并保留共享检出所有权。新模型派发入口不能绕过该标记；原生状态确认空闲后才释放不确定的占用，用户仍需人工接手复验或显式重规划。普通同进程用户中断可继续原生会话；冷加载与不确定提交使用更严格的流程。
- **重复恢复合并为一项操作。** 继续、人工复验及 Git 恢复均有任务级在途合并，进入操作后再次检查当前状态。turn ID 改用 UUID。旧 turn 的成功事件不能接管当前的新 attempt；已确认的集成合并只读核验，不重复调用合并命令；集成记录与实际 Git 图不符则保留现场阻塞。
- **跨进程保存有真实锁。** pipeline 修订检查、原子替换及冷恢复改写处于同一 OS 文件锁中；不同进程对同一修订的不同快照只能有一个成功。生产保存还携带上一笔已确认的磁盘修订：失败后冻结后续写入，丢失确认时先重发字节内容相同的旧快照，再保存最新暂停状态；不能靠增加本地修订号覆盖另一写入者。同一应用数据目录另有应用拥有者锁，第二个应用进程不能在启动时清理第一个应用的活进程。锁随进程退出 / SIGKILL 自动释放，不靠删除过期锁文件猜测拥有权。损坏或含无效 PID 的启动登记会原样保留并阻止启动，不把解析失败当成“没有进程”。

## 三种交付的事务记录

- **合入当前检出：** Git 变更前保存源提交、基线和 merge 意图。若原生响应丢失，重试先读取目标分支、HEAD、工作区、提交父节点以及 git merge-tree 生成的预期树；只有固定父节点和最终树都匹配才确认已合入，不再产生第二个合并。目标仍是原始基线时允许重试原操作；出现无关提交或人工改动时阻塞。确认成功落盘后才清理，后续重复请求只补清理 / 保存。
- **导出补丁：** 写入前保存固定输出路径与源提交。响应丢失后复用该路径；原生只接受字节完全一致的现有产物，不覆盖人工编辑过的补丁。重复点击不生成新的 UUID 文件。正常导出完成后仍可选择合入或保留分支。
- **保留分支：** 删除目录前保存 keep 意图及源提交。若清理已完成但响应或终态保存丢失，通过留存分支的实际 SHA 核对，完成终态登记，不依赖已消失的目录。分支改变则拒绝确认，普通清理仍非强制。交付记录包含源分支与 SHA。

## 用量与状态

新增 V13 迁移，为每个原生 turn 的聚合 Done 保存唯一 usageReceipt；用量行和凭据同一 SQLite 写事务提交。相同事件重放返回原记录，不再入账；同一键但内容不同明确失败，保留原记录。新的 turn 即使 token / 费用相同仍是独立消费。

恢复发现已提交的 attempt 缺少用量凭据时，记录费用缺口，预算按未知费用处理，不能解释为免费；之后真实凭据到达，缺口自动不再计为未知。费用缺口没有推测 token 或伪造账单。已终结 attempt 不会被迟到的 RUNNING 用量 stub 或旧错误改回运行态；重试使用新的 turn / attempt 身份。

计划被明确修改后，失效任务对应的完成凭据、恢复标记和 Git 证明一并失效。历史账单不被 V13 追溯重写或删除，旧格式记录的定价和归因仍须按原有限制理解。

## 故障注入与独立核验

- 派发前后：原生提交记录去重、待派发取消栅栏、活动状态检查，以及前端丢失启动响应后禁止重派发。
- CLI 成功后 / gate 前后：从实际保存的完成凭据快照冷加载，重复继续只执行一次 gate，不产生新模型 turn；没有完成凭据则阻塞。
- 任务提交后 / 集成合并后：保存 committing、committed、merged 和已清理快照后重载；重复恢复只进行必要动作，核对实际分支 / 提交，保留已确认的合并结果。
- 交付后 / 清理前：注入合入、导出和保留分支操作完成但响应丢失，核对意图、复用产物或完成终态；无关目标提交、被修改补丁或留存分支改变都拒绝确认。
- OS / 存储：两个独立进程竞争同一修订，恰好一个成功；真实 SIGKILL 释放文件拥有权；既有原子写强杀回归保证留下完整旧版或新版。重复冷加载不再增加恢复修订。
- 数据库：重复 Done 不重复收费、冲突事件失败、新 turn 单独归因，终态 attempt 不倒退；缺失费用凭据按未知处理。

真实 Git 测试不替换 Git 命令：已验收的二进制修改只提交一次，重复提交恢复不新增提交；最终交付丢失确认后只读认领同一个合并，最终树与验收树完全相同，补丁和留存分支均可复核。证据见 [Git 归档](reliability-evidence/m2e/git/)，可离开原临时目录独立运行：

```sh
python3 scripts/verify-m2e-recovery-evidence.py
```

最终全量检查和原始日志见 [validation.md](reliability-evidence/m2e/validation.md)。前端故障用例使用模拟 IPC，原生锁 / Git / SQLite 用例使用真实本机组件；两者不能合称已做过完整桌面业务恢复。

## 保留的边界

- 不承诺服务商请求的 exactly-once 消费。启动记录表示提交过，不证明实际产生费用；缺少完成凭据时宁可阻塞，不以新的模型调用推测旧请求结果。
- 当前恢复要求原生运行时整体空闲；存在其他活动任务时先等待或中断，不假定进程登记已经能精确归属到某一个恢复任务。
- 同一应用数据目录同时只允许一个拥有者。不同自定义数据目录共享项目、网络文件系统、外部 Git 进程在检查后同时改写、PID 重用及损坏进程登记的完整对抗矩阵未认证；OS 锁是协作锁，不能锁住用户所有外部工具。
- 完成凭据恢复要求固定计划、任务、目录及原生证据；OpenCode 原生历史读取当前返回未知，依靠本轮提交凭据和真实 Git / 新 gate 证据，不虚构历史可见性。旧格式或不完整记录可继续人工接手，不默默重跑模型。
- 恢复会重新运行配置的验收命令，未承诺具有外部副作用的 gate 只执行一次；任务与交付的 Git / 用量记录才按本文规则去重。没有可靠阶段凭据的旧任务不得据此显示成功。
- 最终交付核对使用本机 Git 的 merge-tree --write-tree；不支持该能力时明确失败并保留证据，不以弱化检查兼容。Linux / Windows、真实桌面故障和模型服务端故障仍待 m2g；全量 IPC 既有五个接线缺口仍待 m2f，M2 / M3 未完成。
