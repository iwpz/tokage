# V01 桌面验收：取消热报告

## 首次尝试与修复

2026-11-19（Asia/Tokyo），使用 macOS 隔离构建 `dd37fd1` 和 Codex CLI 0.161.0 的 GPT-6-Luna Medium。正常界面确认热报告已开始，原生记录显示报告请求已进入旧线程，CLI 进程仍在运行。点击 Stop 后报告停止，动作 5 撤销。原始消息随后自动发回旧线程并完成回复，队列没有保留该消息。新线程启动次数为零。[首次失败证据](reliability-evidence/context/v01-20261119/stop-warm-report-first-attempt.json)

报告停止后，Tokage 把原始消息放回队列并显示停止提示。派发结束时把这条提示的完成状态当成普通回复完成，触发了队列发送。修复后，只有普通轮次真实完成才会启动队列下一项。离线回归在旧代码上复现队列清空，修复后通过。另验证普通轮次在派发调用返回前完成时仍会处理下一条队列消息。四个关联测试文件共 77 项通过，前端全量 704 项及类型、隔离检查通过。

## 修复版真实桌面复验

从修复提交 `1b652c73d72f45e88180aff4bb4fa0a963bdc263` 准备独立克隆，经标准 Tauri release 打包后为本地隔离应用重新做 ad-hoc 签名并通过校验。应用数据目录独立，WebView 为临时模式，CLI HOME 使用日常登录环境。通过正常 UI 添加隔离项目、新建会话，以相同的 Codex CLI 0.161.0 和 GPT-6-Luna Medium 只读直聊。Context 使用 Suggest，缓存估价和额外热报告开启，保留 15% 阈值，Debug Provider、Demo 和 Full Auto 关闭。

1. 两轮普通对话结束后，Tokage 估计缓存仍热，且上一轮没有可复用的完整报告。点击 `Apply next turn` 后发送登记的多行消息，原生 CLI 日志记录旧线程收到热报告请求，报告进程仍在运行。
2. 点击一次 `Stop` 后，桌面显示报告已停止，原生记录为 `stopped`，报告进程组退出。动作 1 为 `UNDONE`，目标为空。旧线程在报告轮之后新增零轮，新线程数为零。所有报告前后日志和数据库收据均与上述行为一致。
3. 停止后界面显示 **1 条排队消息**。通过队列的 `Edit` 文本框只读核对，然后点 `Cancel` 退出编辑。32.48 秒后再核对一次，277 字节及其中的中文、标点和 3 处换行逐字节一致。两次检查后消息都留在队列中。

报告在收到完成回执前停止，实际费用未知。撤权、模型报错与跨重启持久化分别留待对应场景验证。[复验结果及哈希](reliability-evidence/context/v01-20261119/stop-warm-report-retest.json)
