# 可靠性优化计划

创建日期：2026-10-16 · 评估基线：`d131a65`

返回 [README](../README.zh-CN.md) · 相关记录：[专项修复清单](fix-todo.md)、[CLI 支持与实机验收](../cli-support-todo.md)

## 目标与范围

让 Tokage 从“可以在人工监督下执行真实需求”，推进到“在明确支持的环境内，可以作为日常开发工具依赖”。

可靠性的基本要求：任务可以失败，但必须准确报告未完成、保留用户工作、控制异常影响，并支持恢复与接手。`DONE`、验收通过和最终交付必须各自有可核对的证据。

本轮优先收口 macOS、默认 `worktree` 隔离和 1–2 个主用 CLI / 模型组合。其他平台、CLI、认证渠道按实际验收记录声明支持范围，不随本轮结果自动扩大。`inplace` 虽非默认模式，仍须修复已知的数据保护问题。

本文是基于当前代码的新一轮可靠性整改计划，补充历史 F 系列与 CLI 验收记录。历史勾选不能替代本轮验收；不以扩大 Provider 数量、增加界面功能或提高测试数量作为本轮完成标准。

## 使用约定

- 所有整改项初始为 `- [ ]`；完成实现、生产接线和相应验收后才能改为 `- [x]`。
- 里程碑按 m1 → m2 → m3 推进；允许提前准备后续测试，但不能跳过前置验收宣布后续阶段完成。
- 子项编号使用 m1a、m1b 等；提交、测试记录与后续问题引用相同编号。
- 已确认缺陷须保留能暴露原问题的回归用例，覆盖真实调用方；替身、库测试、生产入口集成测试和真实 CLI 实机测试分别记录。
- 每项保留：问题与复现条件、修改范围、验证命令、实际结果、失败或跳过原因、证据位置。长期验收证据不得只保存在可能被清理的临时目录。
- `skip`、`ignored`、外部服务不可用和仅有配置文件均不算实机验收通过。不能通过改用其他模型或 Provider 隐藏原组合的失败。
- 里程碑下所有子项和最终验收均通过后，才在里程碑标题追加 ✓。
- 开发过程中由 Tokage 维护 `.tokage/`；本计划不要求人工修改该目录。

## 基线与已确认问题

2026-10-16 本地检查结果：

- 前端：`npm test`，28 个测试文件、172 项测试通过。
- Rust：`cargo test --workspace --locked`，522 项通过、26 项忽略、0 项失败。
- `npm run build`、`npm run check:i18n` 通过。
- `python3 scripts/check-ipc-wiring.py` 退出码为 1，报告 5 个未豁免的无生产调用命令。
- 已核对既有 Claude、OpenCode 1.x / 2.x、Reasonix 桌面 `verified.json`，覆盖两个依赖任务、独立 worktree、门禁、提交与最终合并；本次未重新发起真实模型调用。
- 既有桌面 fixture 使用固定计划、固定模型和串行任务，不代表自然语言需求的自动规划、自动路由和复杂并行已经验收。

独立临时数据库与 Git 仓库中，调用现有 Rust 库复现了以下行为：

- 同一会话 16 线程、10 轮并发保存，160 次调用中 137 次报文件不存在。该实验用于放大并确认临时文件竞态，不是实际使用故障率。
- 两个会话各写一份 `T1` 报告，按 `T1` 查询返回两份，最新结果来自后一个会话。
- 合并不存在的任务分支返回 `Ok(Conflict)`，冲突文件为空，仍生成集成修复任务。
- `inplace` 文件含原有未暂存内容时，调用越界还原会回到 Git index 版本，原有内容未被保留。

以下行为已对照源码，需在整改时补充生产路径复现：写入范围检查异常后继续验收；空验收命令视为通过；全量门禁失败后仍可通过普通确认合并交付。

## m3：形成可日常依赖的使用证据

依赖：m2 完成。目标：通过持续真实使用，验证正确性、可恢复性和人工维护成本，而非仅在验收 fixture 上通过。

### m3a：连续真实需求试用

- [ ] 在选定组合与真实代码库中完成至少 20 个有独立验收依据的真实需求；样本覆盖缺陷修复、新增行为、多文件改动和增量需求。
- [ ] 每个需求记录范围、计划、CLI / 模型、耗时、最终验收、返工与人工介入原因；失败、放弃和外部服务故障同样记录。
- [ ] 连续样本不能只挑选成功任务。为每种需求定义何时算成功、何时算放弃，以及哪些人工介入算救场。
- [ ] 验收：达到样本数量，同时覆盖 m2 的主要真实场景。20 个样本只是本轮最低观察门槛，不解释为可靠性概率证明。

### m3b：校准质量、成本与节省指标

- [ ] 区分首次通过、同窗口修复通过、改派通过、人工接手与放弃；核对任务报告和学习记录中的 `firstPass`，避免固定写入成功。
- [ ] 区分真实费用、等效成本、原生 credits、token 用量和未知值，不能把未知费用当成零成本。
- [ ] 预测通过率展示先验与观察样本的来源；缺少足够本地样本时，不将预测值表述为实测质量保证。
- [ ] 节省评估计入规划、修复、改派及人工救场时间；如要声称优于单一强模型，建立可比任务与同等验收标准。
- [ ] 验收：看板结果能追溯到正确会话与执行记录；指标与实际交付质量一致，不因空验收、串用报告或返工漏计而虚高。

### m3c：消除重复救场与不可解释状态

- [ ] 对试用期间的失败按平台、CLI、网络、规划、执行、验收与交付归因；区分外部故障和 Tokage 自身处理缺陷。
- [ ] 同一原因反复需要人工修数据库、删状态、清 Git 锁或定位隐藏日志时，建立缺陷并修复，不作为正常操作接受。
- [ ] 每个阻塞状态显示原因、已保留的产物和可用的下一步；用户能定位实际工作目录与交付分支并接手。
- [ ] 修复试用发现的问题后，重跑对应故障回归与受影响真实场景，不以重启后暂时正常作为修复依据。
- [ ] 验收：不存在未解释的任务卡死、无提示的状态丢失或持续重复救场；剩余限制有明确范围和操作路径。

### m3d：限定范围的可靠性验收

- [ ] m1 和 m2 全部通过；本轮支持组合、实际验证版本和未覆盖范围已固定并公开。

- [ ] 汇总需求交付结果、人工救场率、端到端耗时和返工成本；给出实际观察值、样本量与限制，不预设一个漂亮比例作为结论。

## 后续扩展原则

完成 m3 后，再按需求扩大 CLI、认证渠道与平台覆盖。每个新增组合重复适用的 m2 验收，更新实际支持范围；不能用一个平台或一个 Provider 的成功代替其他组合验收。

此前约 3–6 周的收口判断仅是冻结范围后的工程粗估。里程碑是否完成始终以上述验收证据为准，不能由工期、勾选数量或测试数量替代。
